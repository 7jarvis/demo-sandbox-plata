# Тест-стратегия: Cardpay sandbox

Документ описывает, что и как проверяется в сервисе виртуальных карт: какие
риски закрываем, на каких уровнях, какими средствами, по каким правилам
тесты пишутся и когда изменение считается готовым к релизу.

## 1. Объект тестирования

Сервис виртуальных дебетовых карт (`app/`): веб-интерфейс и JSON API поверх
одной бизнес-логики.

| Область | Что умеет клиент |
|---|---|
| Регистрация и вход | зарегистрироваться по имени, телефону (+52) и email; войти по одноразовому коду |
| Карты | выпустить до трёх неблокированных карт с названием и дневным лимитом |
| Пополнение | пополнить карту на 1.00–50000.00 MXN, баланс не выше 500000.00 |
| Оплата | оплатить покупку у мерчанта; отказ (decline) записывается в историю с причиной |
| Статус карты | временно заморозить и разморозить; заблокировать навсегда с причиной |
| История | список операций карты с фильтрами по типу и статусу и постраничным выводом |

Контракт API: [`openapi.yaml`](openapi.yaml). Бизнес-правила в тест-кейсах
ссылаются на него, а не на код сервиса.

## 2. Риски и приоритеты

Тестирование строится от рисков. Чем дороже ошибка для клиента и бизнеса,
тем раньше и глубже она проверяется.

| # | Риск | Последствие | Приоритет | Чем закрыт |
|---|---|---|---|---|
| R1 | Двойное списание или зачисление при повторе запроса | прямые финансовые потери, жалобы | Критичный | идемпотентность: TC-TOP-04/05/10, TC-PAY-10 |
| R2 | Списание больше баланса при параллельных платежах | отрицательный баланс, потери | Критичный | TC-PAY-11 (10 параллельных платежей) |
| R3 | Доступ к чужой карте | утечка данных, мошенничество | Критичный | TC-SEC-01/02, TC-UI-08 |
| R4 | Платёж по замороженной или заблокированной карте | мошеннические операции проходят | Критичный | TC-PAY-06/07/08, TC-STAT-04 |
| R5 | Неверный расчёт баланса, лимита, «потрачено сегодня» | неверные данные клиенту, лишние отказы | Высокий | TC-TOP-01, TC-PAY-01…05, TC-HIST-01 |
| R6 | Обход дневного лимита | лимит не защищает клиента | Высокий | TC-PAY-04/05 |
| R7 | Перебор кода входа, раскрытие факта регистрации | захват аккаунта, сбор базы клиентов | Высокий | TC-AUTH-02…05 |
| R8 | Некорректные данные принимаются (формат денег, телефона) | мусор в данных, неверные суммы | Средний | TC-REG-04, TC-TOP-03, TC-PAY-09, TC-SEC-03…05 |
| R9 | Ломается контракт API для клиентов | падение мобильного приложения и партнёров | Высокий | строгие модели ответов на каждом вызове |
| R10 | Пользователь не понимает, что произошло в интерфейсе | обращения в поддержку | Средний | TC-UI-02/03/10/12 |

## 3. Уровни и виды тестирования

```
                 ┌──────────────┐
                 │  UI (19)     │  ключевые сценарии клиента в браузере
                 ├──────────────┤
                 │  API (166)   │  бизнес-правила, границы, безопасность, контракт
                 ├──────────────┤
                 │ ручное/иссл. │  новые фичи, UX, то, что дорого автоматизировать
                 └──────────────┘
```

| Уровень | Цель | Инструменты | Объём |
|---|---|---|---|
| API | Все бизнес-правила, граничные значения, негативные сценарии, права доступа, контракт, конкурентность | pytest, requests, pydantic | основной объём |
| Web UI | Сквозные сценарии клиента: регистрация, вход, выпуск карты, пополнение, оплата, заморозка и блокировка, история; понятность ошибок | Playwright (sync), Page Object Model | только то, что видит клиент |
| Контракт | Каждый ответ API валидируется строгой моделью: лишние и отсутствующие поля, типы, форматы денег, id и дат, инварианты | pydantic в слое service | на каждом вызове, не отдельными тестами |
| Конкурентность | Параллельные платежи и повторы с одним ключом | потоки + барьер | 2 теста, класс `slow` |
| Исследовательское | Новые фичи до автоматизации, удобство интерфейса | чек-листы из `checklists/` | по мере изменений |

Почему так распределено: бизнес-правило дешевле и стабильнее проверить
через API (миллисекунды, нет зависимостей от вёрстки). UI-тест подтверждает,
что правило доходит до клиента понятным образом, поэтому в UI один-два
представителя на правило, а не все границы.

Не входит в объём: нагрузочное тестирование (показано в
[tradebench](https://github.com/7jarvis/tradebench) на k6), кросс-браузерность
(только Chromium), мобильная вёрстка, локализация.

## 4. Техники тест-дизайна

| Техника | Где применяется |
|---|---|
| Классы эквивалентности и граничные значения | суммы (0.99 / 1.00 / 50000.00 / 50000.01), дневной лимит, длины имени, названия карты и мерчанта |
| Таблица решений | причина отказа платежа: статус карты × лимит × баланс; порядок проверок (TC-PAY-08) |
| Переходы состояний | карта `active ⇄ frozen → blocked`; из `blocked` выхода нет (TC-STAT-01…05) |
| Попарное и негативное | формат денег (строка/число/экспонента/запятая), неизвестные поля, битый JSON |
| Сценарное тестирование | сквозные пути клиента в UI |
| Проверка побочных эффектов | после каждого отказа проверяется, что баланс и история не изменились |

## 5. Архитектура автотестов

### API: слои

```
test  →  service  →  adapter  →  http_client  →  HTTP
             └── models (pydantic, строгий контракт)
```

| Слой | Отвечает за | Меняется, когда |
|---|---|---|
| `http_client` | транспорт; лог каждого обмена в Allure с `X-Request-Id` | меняется HTTP-библиотека (только этот файл) |
| `adapters` | метод, путь, заголовки, сериализация | добавился endpoint |
| `services` | бизнес-действие на языке домена; ответ → модель, документированный отказ → `ApiError`, всё остальное → `UnexpectedResponse` | новое бизнес-действие |
| `models` | контракт: поля, типы, форматы, инварианты | меняется контракт |
| тест | сценарий и проверки | — |

Тест не знает об HTTP. Серверная ошибка (5xx) или сломанный ответ никогда
не засчитывается как «ожидаемый отказ».

### UI: Page Object Model

Page object хранит локаторы и действия, проверки — в тесте (`expect` с
автоожиданием). Формы на странице карты — отдельные компоненты, каждый
ограничен своим регионом (на странице два поля «Amount, MXN»).

Приоритет локаторов: роль + доступное имя → label → `data-testid` для
значений без роли (баланс, статус). CSS-классы и XPath не используются.
Локаторы подобраны по дереву доступности живой страницы и проверены на
уникальность. Ошибки полей проверяются как accessible description: это
заодно проверяет, что сообщение связано с полем для экранного диктора.

## 6. Тестовые данные и окружение

- Каждый тест создаёт своего клиента (уникальный телефон и email) и свои
  карты. Общих данных нет, поэтому тесты независимы и могут идти в любом
  порядке.
- Предусловия UI-тестов создаются через API: быстрее и стабильнее, чем
  через интерфейс. Браузер входит через запросы к формам входа, без
  кликов; сам вход через интерфейс покрыт отдельными тестами.
- Удаления клиентов в сервисе нет. Изоляция — уникальные данные;
  в CI база создаётся заново на каждый запуск (`tmpfs`).
- Окружение задаётся переменными: `BASE_URL`, `SANDBOX_OTP_CODE`.
  Запуск против production-хоста запрещён в конфигурации тестов.
- Реальные персональные данные не используются; телефоны и email
  генерируются (`@example.test`).

## 8. Критерии

**Вход в тестирование изменения:** есть требование или тест-кейс, сервис
поднимается `docker compose up --wait`, контракт в `openapi.yaml` обновлён,
если менялся API.

**Готово к релизу:**
- smoke и regression зелёные, повторный запуск без «мигающих» тестов;
- нет открытых дефектов Blocker/Critical;
- новые бизнес-правила покрыты тест-кейсами в `docs/test-cases` и
  автотестами на уровне API, видимые клиенту — ещё и UI-тестом;
- метрики из [quality-metrics.md](quality-metrics.md) в целевых значениях.

## 9. Дефекты

Серьёзность определяется последствием для клиента, а не сложностью
исправления.

| Серьёзность | Пример |
|---|---|
| Blocker | невозможно войти; неверное списание денег; доступ к чужой карте |
| Critical | платёж по заблокированной карте проходит; повтор запроса списывает дважды |
| Major | неверный расчёт «потрачено сегодня»; фильтр истории не работает |
| Minor | неточный текст ошибки; вёрстка ломается на узком экране |

Баг-репорт содержит шаги в бизнес-терминах, ожидаемый и фактический
результат и `X-Request-Id` из Allure-отчёта, по которому запрос находится
в логах сервиса.

## 10. Роли и использование AI

Тесты пишутся с AI-агентом по скиллам из `.claude/skills`
(`api-test-writer`, `ui-test-writer`): сначала анализ требований и
существующих тестов, план и тест-дизайн, переиспользование слоёв, проверка
локаторов на живой странице, quality gates, self-review. Каждое изменение
агента проходит ревью человеком; ожидаемое поведение определяет человек,
а не агент.

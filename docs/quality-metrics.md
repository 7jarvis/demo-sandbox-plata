# Метрики качества

Метрики нужны, чтобы принимать решения (выпускать ли релиз, куда вложить
время), а не ради отчёта. Для каждой указано, как считается, где брать
данные, целевое значение и что делать, если оно не достигнуто.

## Метрики автотестов

| Метрика | Как считается | Источник | Цель | Если не в цели |
|---|---|---|---|---|
| Pass rate regression | прошедшие / все тесты прогона | Allure, JUnit-проверка в PR | 100 % на `main` | релиз блокируется до разбора каждого падения |
| Flaky rate | тесты, которые в одном коммите и падали, и проходили / все тесты, за 30 дней | история Allure (Retries, Trend), перезапуски CI | 0 %, допустимо < 1 % | тест помечается задачей и чинится в течение спринта; `skip` без задачи запрещён |
| Время smoke | длительность шага `pytest -m smoke` | GitHub Actions | ≤ 1 мин | лишнее выносится из smoke в regression |
| Время regression | длительность шага `pytest -m regression` | GitHub Actions, Allure Duration trend | ≤ 5 мин | распараллеливание (`pytest-xdist`), перенос проверок с UI на API |
| Время от push до отчёта | от push до деплоя Pages | GitHub Actions | ≤ 10 мин | кеш зависимостей и браузеров, параллельные джобы |
| Доля API / UI | тесты API / все тесты | маркеры `api`, `ui` | ≥ 80 % API | бизнес-правила переносятся с UI на API |

## Метрики покрытия

| Метрика | Как считается | Цель |
|---|---|---|
| Покрытие требований | бизнес-правила из `openapi.yaml` и тест-стратегии, у которых есть тест-кейс / все правила | 100 % |
| Автоматизация тест-кейсов | кейсы со ссылкой на автотест / все кейсы в `docs/test-cases` | ≥ 90 %; остальное — осознанно ручное с причиной |
| Покрытие рисков | риски из тест-стратегии (R1–R10), закрытые хотя бы одним автотестом | 100 % для Критичных и Высоких |
| Покрытие endpoint-ов | endpoint-ы с позитивным и негативным тестом / все endpoint-ы | 100 % |

Связь «кейс → автотест» прослеживается в обе стороны: в тест-кейсе указан
автотест, в Allure у теста есть ссылка на кейс (`@case("TC-PAY-01")`) и
метка `case_id`.

## Метрики дефектов

| Метрика | Как считается | Цель | Зачем |
|---|---|---|---|
| Утечка дефектов (DDP) | дефекты, найденные до релиза / все дефекты релиза, включая найденные после | ≥ 90 % | показывает, насколько тестирование ловит проблемы до клиента |
| Дефекты в production по серьёзности | количество Blocker / Critical после релиза | 0 Blocker, 0 Critical | главный индикатор качества для бизнеса |
| Время до обнаружения | от коммита с дефектом до красного теста | в том же PR | дефект, пойманный в PR, дешевле на порядок |
| Регрессионные дефекты | дефекты в ранее работавшей функциональности | → 0 | на каждый такой дефект пишется автотест, который падал бы на нём |
| Отклонённые баг-репорты | «не баг» / все заведённые | < 10 % | качество анализа требований и баг-репортов |

## Текущие значения

На последнем прогоне `main` (см. [Allure](https://7jarvis.github.io/demo-sandbox-plata/)):

| Метрика | Значение |
|---|---|
| Тестов всего / smoke | 185 / 18 |
| Pass rate | 100 % |
| Время smoke / regression (шаг pytest в CI) | ~5 с / ~15 с |
| От push до опубликованного отчёта | ~4 мин |
| Доля API | 166 / 185 ≈ 90 % |
| Автоматизация тест-кейсов | 72 из 74 (97 %), см. [test-cases/README.md](test-cases/README.md) |
| Риски R1–R10 | все закрыты автотестами |
| Endpoint-ы с позитивным и негативным тестом | 12 / 12 |

## Как это используется

- **Решение о релизе:** pass rate 100 %, нет открытых Blocker/Critical,
  новые правила покрыты (см. критерии в тест-стратегии).
- **Ретро раз в спринт:** flaky rate, время прогона, регрессионные дефекты.
  Каждый регрессионный дефект — вопрос «какой тест должен был его поймать».
- **Планирование:** низкая автоматизация кейсов или рост ручных проверок
  перед релизом — сигнал заложить время на автотесты в следующий спринт.
